Task 1: Create Two SQL Views
View 1 — Active Customer Metrics

Create:

vw_active_customers

Purpose:

Provide a consistent definition of customer activity and revenue over the rolling 30-day period.

Required columns:

customer_id
customer_name
segment
order_count_30d
revenue_30d
last_order_date
days_since_order

Example:

CREATE VIEW vw_active_customers AS
SELECT
    c.customer_id,
    c.customer_name,
    c.segment,
    COUNT(DISTINCT o.order_id) AS order_count_30d,
    COALESCE(SUM(o.order_amount), 0) AS revenue_30d,
    MAX(o.order_date) AS last_order_date,
    DATEDIFF(CURRENT_DATE, MAX(o.order_date)) AS days_since_order
FROM customers c
LEFT JOIN orders o
    ON c.customer_id = o.customer_id
    AND o.order_date >= CURRENT_DATE - INTERVAL 30 DAY
WHERE c.deleted_at IS NULL
GROUP BY
    c.customer_id,
    c.customer_name,
    c.segment;

-- View: vw_revenue_by_region
-- Purpose: Centralize regional revenue reporting.
-- Business question: Which regions generate the most revenue?

CREATE VIEW vw_revenue_by_region AS
SELECT
    c.region,
    COUNT(DISTINCT c.customer_id) AS customer_count,
    COUNT(DISTINCT o.order_id) AS order_count,
    SUM(o.order_amount) AS total_revenue,
    AVG(o.order_amount) AS avg_order_value
FROM customers c
JOIN orders o
    ON c.customer_id = o.customer_id
WHERE c.deleted_at IS NULL
  AND o.order_amount > 0
GROUP BY c.region;

Populate the Table
INSERT INTO agg_daily_metrics
SELECT
    DATE(o.order_date) AS aggregation_date,
    'total_revenue' AS metric_name,
    SUM(o.order_amount) AS metric_value,
    COUNT(*) AS row_count,
    CURRENT_TIMESTAMP AS updated_at
FROM orders o
WHERE o.order_amount > 0
GROUP BY DATE(o.order_date);

Task 4: Define Data Layer Naming Conventions

Create:

data_layer_conventions.md

Use the following conventions:

# Clean Data Layer Naming Conventions

## Views

- Prefix: `vw_`
- Pattern: `vw_[business_entity]_[metric]`
- Views contain reusable business logic.

Examples:
- `vw_active_customers`
- `vw_revenue_by_region`

## Pre-Aggregated Tables

- Prefix: `agg_`
- Pattern: `agg_[grain]_[subject]`
- The name must communicate the aggregation grain.

Examples:
- `agg_daily_metrics`
- `agg_hourly_revenue`

## Aggregated Table Columns

Every aggregation table should include:

- A date/time grain column
- Metric name or clearly named metric columns
- `row_count`
- `updated_at`

## Benefits

- Object purpose is clear from its name.
- Dashboard developers use consistent sources.
- Business logic is centralized.
- Metric definitions cannot silently drift between dashboards.
- Aggregated data improves dashboard query performance.

Bonus Questions
1. What happens when a view definition changes?

A view normally stores the SQL definition rather than a separate copy of its result. When the view definition is changed, subsequent queries use the updated definition.

However, dashboards may still show cached data if they use application-level or database-level caching. Therefore, changes should be tested before deployment.

2. What happens between hourly aggregation refreshes?

The pre-aggregated table only contains information from its most recent refresh. New events occurring after the refresh are not reflected until the next aggregation.

For near-real-time dashboards, possible approaches include:

More frequent refreshes.
Incremental aggregation.
Querying recent raw data alongside historical aggregates.
Streaming/event-driven pipelines.
